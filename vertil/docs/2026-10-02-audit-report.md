## 1. Что было сломано и что найдено

### B1. Главная причина «гула вентиляторов» — чужой демон перетирал наши PWM

**Симптом:** вентиляторы то тихо, то громко, плавающий гул без связи с температурой.

**Причина:** `omen-space-daemon` (root, `omen-space-daemon.service`) держал
собственный FanService с мониторингом **раз в секунду** и своей кривой
`custom [[40,0],[55,15],[70,35],[85,60],[100,100]]` — то есть на простое
давал **0 % PWM (0 RPM)**. Наша запись держалась ровно до следующего его
тика и перетиралась.

**Фикс:** сервис остановлен и отключён — `systemctl disable --now
omen-space-daemon.service`. Проверка: `victus-kbd fans set-pwm 200` держится
стабильно, 4700 RPM, на протяжении минут наблюдения без единого возврата.

### B2. Один канал PWM на обе вентиляторы (hp-wmi)

На этом железе `pwm2` отсутствует — запись идёт только в `pwm1`, но он
управляет **обоими** каналами. `fanctl` считал, что левого канала нет, и
возвращал только `pwm1`, а TUI/лаборатория писали в несуществующий `pwm2`.

**Фикс** (`vertil/tools/fanlib.py`): авто-детект одноканального режима —
`shared_pwm`, `channels`; `read()` возвращает `pwm2 = pwm1`; `set_pwm()`
пишет `max(p1, p2)` в `pwm1` (запись второго канала тихо пропускается).
`presets.json` — ключ `fans.single_channel_note` как документация железа.

### B3. «Нет прав» там, где атрибута просто нет

`open()` на несуществующем sysfs-узле даёт `FileNotFoundError`, который
обрабатывался как отказ прав — в логах и статусе враньё.

**Фикс:** `_w()` сначала `exists()`, потом `access(W_OK)`, потом `open()`.
Теперь два разных кода: **rc=2 — «нет атрибута»** (железо/драйвер не дал),
**rc=1 — «нет прав»** (нужен root). Офлайн-тест проверяет оба случая.

### B4. Ложные пики температур и аварийный «сход с ума»

Одиночный выброс температуры (шум датчика / пик по VRM) мгновенно
переводил контроллер в EMERGENCY и хлопал обе вертушками на максимум,
спад шёл потом по кривой — отсюда «внезапно орёт без причины».

**Фикс:**
* `TempFilter` в `Sensors` — медиана по 3 снимкам + ограничение скорости
  нарастания (12 °C/с) и спада (6 °C/с); сырьё сохраняется в `t_*_raw`,
  чтобы аварийная логика могла смотреть на **неотфильтрованное** значение;
* `Smart._hyst()` — гистерезис входа/выхода (`smart.hysteresis up/down`)
  в точках разворота кривой: вентилятор больше не «качает» на границе;
* авария по **сырой** температуре — фильтр не имеет права задержать
  настоящий перегрев.

### B5. Лаборатория не могла писать и искала не те датчики

`vertil/tools/lab/phase.py` писал напрямую в `pwm1`/`pwm2` (B2), `start.sh`
искал `hwmon7`/`hwmon5` по захардкоженным номерам. На другой машине или
после ребута это просто не работает.

**Фикс:** запись через `fanlib.Fans` (одноканальный PWM учтён),
`Sensors.read` — fallback `pwm2→pwm1`, `start.sh` определяет hwmon **по
имени чипа**, а не по номеру.

### B6. `hyprctl keyword monitor` возвращает код 0 и ничего не делает

Герцовка «по тихому» не переключалась: `hyprctl` печатал
*«keyword can't work with non-legacy parsers. Use eval.»* и завершался
**rc=0** — по коду возврата это выглядело успехом.

**Фикс:** установлен `wlr-randr`, герцовка через него с **проверкой
результата** (перечитываем фактический режим). Проверено вживую:
144 → 60 → 144.

### B7. `nvidia-smi -pl` отвечает rc=0 с «not supported»

Классический ложный успех: команда завершилась успешно, лимит не применился.
Разобрано отдельно, показывается как `skipped`, а не как применённое.

### B8. Точка отката «запоминала» уже включённую печатную машинку

`power-profiles-daemon` **сам** пишет и `platform_profile`, и
`energy_performance_preference` (проверено: `set balanced` →
`profile=balanced epp=balance_performance`). Снимок внутри `victus-power`
делался *после* вызова PPD, поэтому в точку отката попадало уже изменённое
состояние, и выключение возвращало **не** базовое.

**Фикс:** явная подкоманда `victus-power snapshot`, которую TUI вызывает
**самой первой**, до PPD; `apply` чужой снимок больше не перетирает.

**Второй слой (проверено на живом сбое).** Снимок перетирался и другим
путём: TUI запущен, когда система **уже** в режиме (ручной `victus-power
apply`, падение TUI посреди режима) — тогда `PREV` отсутствует, и TUI
снимал baseline с уже изменённой системы. Отключение «возвращало»
печатную машинку. `victus-power snapshot` теперь **идемпотентен**:

* снимок уже есть → `skipped: "точка отката уже есть — не перетираю"`;
* `looks_typewriter()` видит `no_turbo=1` / PL1 ≤ 20 Вт /
  `max_perf_pct ≤ 50` / `platform_profile=low-power` → **отказ**,
  `failed: "система уже в режиме печатной машинки … — baseline не записан"`;
* TUI показывает отказ (режим помечается `partial`), а не «точка
  отката сохранена»;
* `state/power_prev.json` стирается **только после чистого отката**
  (пустой `failed`), иначе PPD/герцовка — единственные оставшиеся
  следы baseline.

**Проверка — 4 цикла подряд, идеальный round-trip:**

```
ON   tw=True  ppd=power-saver hz=60.0  profile=low-power   epp=power               pl1=15.0 noturbo=1 maxperf=40
OFF  tw=False ppd=balanced    hz=144.0 profile=balanced    epp=balance_performance pl1=55.0  noturbo=0 maxperf=100
ON2  tw=True  ... (то же)                                                    OFF2 ... (то же)
final: balanced / balance_performance / 55.0 Вт / turbo on / 100 %
```

## 2. Режим «Печатная машинка»

Одна кнопка в новой вкладке «Питание» (и CLI `victus-power`). Включается —
ноутбук тихий и медленный, выключается — всё возвращается ровно туда, где было.

| Ручок | Значение «печатной машинки» | Кто пишет |
|---|---|---|
| `platform_profile` | `low-power` | root |
| PPD-профиль | `power-saver` | user |
| Intel P-state `no_turbo` | `1` (турбо выкл) | root |
| `max_perf_pct` | `40` | root |
| RAPL PL1 / PL2 | 15 Вт / 30 Вт (база 55/115) | root |
| CPU governor / EPP | `powersave` / `power` (все 16 ядер) | root |
| Частота панели | 60 Гц (база 144) | user, `wlr-randr` + проверка |
| Вентиляторы | BIOS AUTO (тихая кривая) | user, `victus-kbd` |
| `nvidia-smi -pm 0`, `-pl` | энергосбережение дискретки | root (частично — см. §4) |

**Порядок выполнения важен:** PPD и герцовка → **напоследок** root-часть,
иначе PPD затрёт уже выставленные профили.

**Что ещё входит в режим (второй проход ТЗ):**

| Ручок | Значение | Кто пишет |
|---|---|---|
| Wi-Fi `power_save` | `on` (`iw dev wlo1`, **без shell**) | root |
| Bluetooth | `rfkill block bluetooth` (только если есть rfkill-устройство) | root |
| `scaling_max_freq` | 1 800 000 (жёсткий потолок, все 16 ядер) | root |
| dGPU Runtime D3 | `power/control=auto` + ожидание `runtime_status=suspended` | root |

### Ползунок потолка 5–25 Вт — на всю систему

Ниже таблицы (15/30 Вт, `max_perf_pct=40`, 1.8 ГГц) — это **позиция 15** на
новом ползунке. Вкладка умеет перенастраивать весь план от 5 до 25 Вт, и
это потолок **ноутбука целиком**, а не только CPU:

| Ручок | Формула от N (5..25) | Кто пишет |
|---|---|---|
| RAPL PL1 / PL2 | `N` / `2·N` | root |
| `max_perf_pct` | `20 + (N-5)·2` (5 → 20 %, 15 → 40 %, 25 → 60 %) | root |
| `scaling_max_freq` | `1.0 + (N-5)·0.08` ГГц на все 16 ядер, с ограничением по `cpuinfo_max_freq` (15 → 1.8 ГГц, 25 → 2.6 ГГц) | root |
| дискретка | `power/control=auto` + ожидание `runtime_status=suspended` (честный `skipped`, если не успела) | root |

* ползунок свой (`WattsBar`) — в Textual 8.2.8 встроенного `Slider` нет:
  клик, стрелки, PgUp/PgDn, Home/End, колесо, `Changed` только от
  пользователя (иначе реактивное присвоение цепляло бы ещё одну запись);
* пока режим выключен — ползунок мёртв и root-хелпер вежливо отказывает
  (`rc=1` + JSON); чтобы снять это ограничение, пришлось поднять порог
  `power_core.mode()` с 20 на 30 Вт — иначе ползунок гасил сам себя при
  значениях выше 20;
* операция идёт в отдельном `_mode_busy` (не в общем `_busy`), иначе
  серия «стрелка→» схлопывалась в одно нажатие: общий busy гасил слайдер
  и снимал фокус;
* подсказка разделена на три ключа: сам режим, **реальный** расход системы
  и хвост относительно цели 5 ч (9.4 Вт). Заодно убрано захардкоженное
  «дискретка спит» — это читается из ридаута.

### Индикация состояния в TUI — по железу, а не по последнему клику

Вкладка «Питание» держит **одну точку правды** — `PowerTab._sync(st)`,
которую вызывают загрузка, тик раз в 5 с и окончание переключения.
Всё в ней привязано к `power_core.status()`, то есть к **root-снимку и
sysfs**, а не к `self.typewriter`:

* чип-подпись `ВКЛ` / `выкл` / `частично` (+ класс `on`/`warn`);
* тумблер перетягивается по факту (`if not busy and sw.value != on`);
* во время операции `sw.disabled = True` — второй клик невозможен;
* после клика состояние перечитывается: `failed` → красная строка и
  тумблер возвращается в реальность, `partial` → жёлтая «режим включён
  не полностью», расхождение → «состояние железа не изменилось»;
* ридауты: профиль, процессор (+ «до N МГц»), экран, дискретка
  (+ «dGPU спит»), **радио**, вентиляторы, батарея — 157 ключей в обеих
  локалях, паритет ru/en;
* **подсказка под чипом тоже привязана к факту**: ключи
  `tui.pwr_hint_typewriter` / `tui.pwr_hint_full` описывают реальный
  режим (`«тихий ноутбук: частоты и дискретка приглушены, 60 Гц…»` при
  включённом и «полная мощность…» при выключенном). Изначально они были
  названы и применены наоборот — чип `ВКЛ`, а подпись обещала турбо и
  144 Гц на фоне фактических 15 Вт/60 Гц (поэтому переименованы);
* **тумблер виден**: трек включённого состояния золотой `#ffd766` с тёмной
  головкой, выключенное состояние и hover подняты по контрасту;
* **строка заряда считает остаток**: `battery()` возвращает
  `capacity/status/watts/hours` из `energy_now`/`energy_full`/`power_now`
  (fallback `current_now × voltage_now`) → `91% · Discharging · 15 Вт ·
  ≈ 3 ч 13 мин`. Оценка измеренная, а не константа: она сама следует за
  нагрузкой браузера;
* **JSON не вываливается в строку ошибки**: `victus-power` отдаёт `rc=1`
  вместе с валидным JSON, когда сам честно сообщил об ошибке;
  `power_core._json` разбирает stdout **до** проверки кода возврата.

### Честный root-статус

`victus-power status` по умолчанию **не вызывает `nvidia-smi`**: каждый
такой запрос будит дискретку из Runtime D3, а опрос раз в 5 с свёл бы
на нет всё усыпление. Для явного запроса есть `status --nvidia`.
`restore` тоже не будит карту, если лимиты не менялись, а `apply`
пропускает `-pm`/`-pl`, когда результат был бы тождественным.

**Безопасность.** Отдельный бинарник `bin/victus-power` под NOPASSWD-правило
`/etc/sudoers.d/victus-power` с **жёстким белым-листом**: команда, аргумент и
значение проверяются на регэксп, на sysfs уходят только конкретные пути из
зашитого списка. Плюс `visudo -c` чисто. Переключение в TUI идёт в воркере,
интерфейс не блокируется, показания обновляются раз в 5 с.

**Откат.** Точка отката создаётся **до первого включения**:
`/var/lib/victus-suite/power-state.json` (0600) + пользовательская
`state/power_prev.json` (PPD и герцовка). `victus-power restore` применяет
корневой снимок и проверяет запись через 1 с — если EC/прошивка перетёрла
(RAPL на этом железе имеет право откатиться), это честно рапортуется, а не
выдаётся за успех.

## 3. Идеи Omen Space — что взято, что нет

| Идея | Решение |

## 4. Известные ограничения (не баги, но честно)

1. **Дискретку полностью не выгрузить**: `/dev/nvidia0` держат Hyprland,
   `omen-gui` и `voxtype-osd-gtk` → `rmmod nvidia` вернёт «module in use».
   Режим ограничивается power-ручками; для MUX реально работает только
   запись `gpu_mux_mode` (переключение требует перезагрузки).
2. **`nvidia-smi -pl` на этой прошивке не поддерживается** — показывается
   как skipped, лимит не применяется.
3. **hp-wmi не отдаёт setpoint**: чтение `pwm*` ≈ 0.95× от записанного,
   запись применяется с задержкой, после отпускания EC возвращает свой
   уровень. Статус показывает последнюю команду (поведение прежнее).
4. **Единственный тест-сьют в репозитории** — `vertil/tools/lab/test_fanlib.py`
   (20 кейсов). Остальные пробы живут в `/tmp/opencode/` и в репозиторий не
   перенесены — это дорожная карта R5.
5. **`nvidia-smi` будит дискретку на 5–15 с** — из-за этого статус не
   спрашивает про GPU по умолчанию (см. §2), а `apply` дожидается
   `suspended` лишь 4 с и дальше честно пишет «уйдёт в Runtime D3 сама
    после idle». Наблюдение: карта уходит в D3 в течение секунд после
    того, как её перестали дёргать; держатели `/dev/nvidia0` (Hyprland,
    voxtype) этому **не мешают**. Расход проснувшейся вхолостую карты —
    **17 Вт ≈ 12 с**, далее 1.8 Вт и уход в сон, поэтому усыпление здесь
    даёт больше, чем все остальные ручки режима.
6. **`scaling_max_freq` не берётся с первого раза**: intel_pstate молча
   отклоняет запись сразу после смены `no_turbo`/`max_perf_pct`, а через
   0.2–0.5 с начинает принимать (замер: **16/16 ядер с ретраем,
   0/16 без**). Без ретрая это выглядело бы как «все 16 ядер отказали».
   `write(..., attempts=4, delay=0.2)` стоит **только** на частотных
   ручках — для обычных мгновенный отказ означает реальную проблему.
7. **Вкладка «Вентиляторы» тоже владеет вентиляторами**: при монтировании
   (и при пересборке экрана после смены языка) она восстанавливает выбор
   из `state/fan_mode.json` и мгновенно отменяла бы только что включённый
   тихий режим. `vertil_core.power_typewriter()` гасит и восстановление
   режима, и записи SMART-автопилота, пока включена «печатная машинка».
   Обратное тоже верно: выключение возвращает **прежний** режим вентиляторов
   (из `power_prev.json`), а не оставляет тихий.

## 6. Как пользоваться и как откатить

```bash
victus-power status [--json]      # что сейчас
victus-power snapshot             # точка отката (TUI делает сам перед включением)
victus-power apply typewriter     # включить режим
victus-power restore              # вернуть всё, как было
victus-power mux hybrid|discrete  # MUX (нужна перезагрузка)
victus-power watts 10             # потолок на всю систему (режим должен быть включён)

# подсветка с клавиатуры корпуса (root не нужен — NOPASSWD)
sudo -n victus-kbd power toggle|on|off
```

В интерфейсе: вкладка **«Питание»** → тумблер «Печатная машинка» и ползунок
5–25 Вт; вкладка **«Клавиатура»** → тумблер подсветки.

**Горячие клавиши подсветки.** Штатный байнд Omarchy
(`omarchy-brightness-keyboard`) на этой машине всегда падает: во Victus нет
`/sys/class/leds/*kbd_backlight*`. Перепривязано в
`~/.config/hypr/bindings.lua`: `XF86KbdLightOnOff` → `power toggle`,
`XF86KbdBrightnessUp` → `power on`, `XF86KbdBrightnessDown` → `power off`.
Команда пишет **и EC, и `state/last_state.json`** — иначе вкладка показала бы
своё старое значение; внешний опрос в `kbd_tab` (1.5 с) подтягивает тумблер
и цвет. Нужен `hyprctl reload` после правки биндов.

**Полный откат аудита:** `git switch main` (или
`git reset --hard pre-audit-2026-10-02` на ветке) + восстановление сервиса:
`systemctl enable --now omen-space-daemon.service` — **но это вернёт
перетирание PWM**, то есть возврат к исходной проблеме B1.
