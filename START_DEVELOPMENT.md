## 0. Правила взаимодействия для AI-разработчика

> **Важно:** пользователя **постоянно меняет AI-агентов**. Любой новый агент
> должен сходу понять контекст только по `START_DEVELOPMENT.md` + `PROGRESS_LOG.md`
> и **не задавать лишних вопросов**. Поэтому журнал ведётся максимально строго.

### 1. Пошаговая проверка (никакой работы вслепую)

```
сделал 1 минимальное изменение  →  ОСТАНОВИЛСЯ  →  спросил пользователя:
«Я применил изменения: цвет поменялся? Датчики считываются?»
```

- Переход к следующему шагу **ТОЛЬКО** после явного ответа пользователя **«Да»**.
- Нет ответа / есть сомнения — шаг не считается сделанным.
- Никогда не делать «пачку» изменений до проверки предыдущего.

### 2. Авто-коммиты после подтверждения

- После **каждого успешного и подтверждённого пользователем** шага:
  `git add -A && git commit -m "..."`
  и `git push` на GitHub (ветка `main`).
- Коммит без подтверждения пользователя — **запрещён**.
- История должна быть чистой: один коммит = один подтверждённый шаг.

### 3. Журнал `PROGRESS_LOG.md`

- Файл **всегда** обновляется после каждого изменения, в конце работы.
- Обязательные поля:
  - точные **дата и время** последнего изменения;
  - **что конкретно сделано** и **какие файлы изменены**;
  - **костыли, нюансы, найденные ошибки** (если были — писать честно);
  - **точный следующий шаг** («План на сейчас / на завтра»).

### 4. Автономность контекста

- `PROGRESS_LOG.md` ведётся так, чтобы **новый агент за 5 секунд** понял
  статус без объяснений от пользователя.
- Каждая запись журнала должна быть самодостаточной: где мы, что осталось,
  что проверено, что не проверено.
- После смены агента: прочитать `START_DEVELOPMENT.md` → `PROGRESS_LOG.md`
  → продолжить с последнего «Следующего шага».

## 1. Что это за проект

**OMEN Gaming Hub for Linux** (локальная папка `victus-suite`, репозиторий
`victus-suite`) — аналог OMEN Gaming Hub для Linux:
подсветка клавиатуры HP Victus/OMEN, режимы питания, вентиляторы,
мониторинг и оверлей (замена `Shift+F2`).

Проект создаётся в формате **Vibe Coding** — разработка при активной
поддержке AI-агента, в тесной связке с пользователем.

Целевая тестовая машина: **HP Victus 16-r0xxx** (i5-13500H, RTX 4060),
ядро `7.2.5-3-omarchy`, Omarchy/Arch, Hyprland.

### 2.2. ДОСТУПНО В ЯДРЕ, ЧАСТЬ УЖЕ ОБЁРНУТА (следующие шаги)

> Всё это уже лежит в sysfs и проверено на этой машине — не надо изобретать.

```bash
# ВЕНТИЛЯТОРЫ (hwmon "hp", driver hp-wmi) — ✅ ОБЁРНУТО с v1.1.0-beta:
#   vertil/tools/fanlib.py (чтение + контроллер), vertil/tools/fanctl.py
#   (запись), вкладка TUI «Вентиляторы», `victus-kbd fans <cmd>`
/sys/class/hwmon/hwmon7/pwm1_enable    # 0=MAX, 1=MANUAL, 2=AUTO
/sys/class/hwmon/hwmon7/pwm1           # 0..255 (только при enable=1)
/sys/class/hwmon/hwmon7/pwm2           # второй канал (общий enable)
/sys/class/hwmon/hwmon7/fan1_input     # RPM CPU (правый)
/sys/class/hwmon/hwmon7/fan2_input     # RPM GPU (левый)

# ТЕМПЕРАТУРЫ — читаются в TUI через fanlib, отдельной команды `monitor` пока нет
/sys/class/hwmon/hwmon8/temp1_input    # coretemp Package (миллиградусы)
/sys/class/hwmon/hwmon1/temp1_input    # acpitz
nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader

# РЕЖИМЫ ПИТАНИЯ (аналог Comfort/Default/Performance) — ❌ не обёрнуто
/sys/firmware/acpi/platform_profile            # low-power|balanced|performance
powerprofilesctl set performance|balanced|power-saver
```

**Важные тайминги** (из `docs/04-ventilyatory.md`):
BIOS требует stagger **10 с** между вентиляторами; режим ручного управления
держится **120 с** → watchdog должен переприменять кривую каждые **90 с**;
обязательный fail-safe: CPU ≥ 92 °C / GPU ≥ 83 °C → немедленно AUTO.

## 3. Технологии (зафиксировано)

- **Язык разработки: Python 3** (самый документированный и удобный
  для TUI/CLI; весь текущий код уже на нём).
- **TUI-интерфейс: библиотека Textual** (в системе — `python-textual` 8.2.8
  из pacman; **в 8.2.8 нет виджета `Slider`**, поэтому слайдер написан
  вручную — `bin/tui/slider.py` `MiniSlider`).
- **Локализация: `locales/`** (JSON), по умолчанию **английский (us)**,
  доступен русский. См. §6.
- Стиль кода: без комментариев-«воды», функции маленькие, ошибки — через
  `die()` + запись в лог.

## 5. Правила работы для следующего разработчика (правила агента)

0. **Сначала прочитать `PROGRESS_LOG.md`** — там текущий статус и точный
   следующий шаг. Порядок: `START_DEVELOPMENT.md` → `PROGRESS_LOG.md` → работа.
   Подробные правила общения — §0 этого файла.
1. **Двигаться строго по этапам:** от самого минимума к максимуму.
   Никакого усложнения до того, как заработает база.
2. **Любое действие, изменение архитектуры или добавление новых функций
   ТРЕБУЕТ предварительного согласования с пользователем.**
3. **Не принимать самостоятельных решений по спорным моментам** — задавать
   уточняющие вопросы.
4. **При возникновении ошибок или непоняток сразу обращаться к пользователю**
   за подтверждением.
5. Всё новое — в **одну папку проекта**: код в `bin/`, тексты в `locales/`,
   конфиги в `config/`, логи в `logs/`, отчёты в `state/`, заметки в `docs/`.
6. Каждое действие логируется (`logs/victus.log`), при проблеме —
   `victus-report` и показать пользователю.
7. Сообщения интерфейса — **на русском** (перевод через `locales/`),
   логи — технические, на английском.
8. Не трогать EC вне известных offset'ов (`0x08..0x0A`), всегда делать
   бэкап перед экспериментами.
9. Не форсить `sudo`, не добавлять NOPASSWD без согласования.

## 6. Локализация (i18n)

```
locales/ru.json      русский (исходник текстов)
locales/en.json      английский (по умолчанию, fallback)
config/locale         файл с текущим языком (содержит: en)
bin/i18n.py          загрузчик: t("раздел.ключ", параметры=...)
```

Приоритет языка: `VICTUS_LANG` → `config/locale` → `ru`.

**Как добавить язык:**
1. `cp locales/ru.json locales/de.json`
2. перевести значения (ключи не трогать)
3. `echo de > config/locale` или `VICTUS_LANG=de Changer list`

Добавление новой строки: дописать ключ в `ru.json` **и** `en.json`,
вызывать `t("раздел.ключ", arg=...)`.
